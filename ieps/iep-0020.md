## Introduction

A C2PA Manifest binds provenance information to an asset. Its hard binding is a cryptographic hash
of the asset bytes. Platforms often remove the C2PA Manifest when they process an asset. A change to
the bytes, for example by resizing or re-encoding, also breaks the hard binding.

A soft binding is a fingerprint or watermark that helps in both cases. A resolver uses it to find
the C2PA Manifest of an asset that no longer carries it. A validator uses it to compare an asset
with the content from which the soft binding was extracted or generated.

The `io.iscc.v0` soft binding value is a sequence of ISCC-UNITs. Each ISCC-UNIT describes a
different aspect of an asset.

An equal Instance-Code shows that an asset has exactly the bytes from which the ISCC soft binding
was generated. For each other ISCC-UNIT, the distance between two codes indicates how much that
aspect has changed. A resolver uses these distances to select candidates from its catalog. A
secondary check suited to the use case and media type confirms or rejects each candidate.

## Scope

This document specifies the C2PA soft binding algorithm `io.iscc.v0`.

______________________________________________________________________

## Terminology

The terms ISCC-UNIT, ISCC-HEADER, ISCC-BODY, ISCC-CODE, MainType, SubType, Version and Length apply
as defined in ISO 24138:2024 and [IEP-0001](iep-0001.md). The terms soft binding, claim generator,
validator, C2PA Manifest, C2PA Manifest Store, claim signature, hashed URI and hard binding apply as
defined in the C2PA Technical Specification.

**resolver** : service that returns C2PA Manifests for a soft binding query

**ISCC-SEQ** : byte string formed by concatenating the byte representations of one or more
ISCC-UNITs

**ISCC soft binding** : ISCC-SEQ in a `blocks[].value` of a `c2pa.soft-binding` assertion with `alg`
equal to `io.iscc.v0`

**source** : complete byte stream into which a claim generator embeds a C2PA Manifest Store,
including any C2PA Manifest Store that the byte stream already contains

**query asset** : asset for which C2PA Manifests are searched by soft binding

**candidate** : C2PA Manifest with an ISCC soft binding that has an ISCC-UNIT equal or similar to an
ISCC-UNIT generated from a query asset

**exact match** : equality of a 256-bit Instance-Code of an ISCC soft binding and the Instance-Code
generated from an input

**featureless Image-Code** : Image-Code whose ISCC-BODY, divided from its first bit into consecutive
64-bit segments, has at least one segment with fewer than 8 bits set to 1

## Soft Binding Value

### ISCC-SEQ Format

An ISCC-SEQ shall satisfy all of the following:

1. It shall consist of one or more ISCC-UNITs of MainType META (0), SEMANTIC (1), CONTENT (2), DATA
    (3) or INSTANCE (4).
2. Each ISCC-UNIT shall be coded as its ISCC-HEADER immediately followed by its ISCC-BODY.
3. Each ISCC-HEADER shall use the variable-length nibble encoding of ISO 24138:2024.
4. Each Length field shall have a value from 0 to 7, for an ISCC-BODY of 32 × (Length + 1) bits.
5. The ISCC-UNITs shall be concatenated without separators, length prefixes or trailing bytes.

The order of the ISCC-UNITs is not significant. An ISCC-SEQ may contain several ISCC-UNITs with the
same MainType, SubType and Version.

The canonical form of an ISCC-SEQ is `ISCC:` followed by the Base32 encoding of its bytes, as for
any ISCC (see [IEP-0001](iep-0001.md)). An ISCC soft binding contains the bytes. The Soft Binding
Resolution API uses their base64 encoding.

### Decoding

A decoder shall process an ISCC-SEQ from offset 0 as follows:

1. Decode the ISCC-HEADER at the current offset. Reject the ISCC-SEQ if the bytes end before the
    ISCC-HEADER is complete, or if the ISCC-HEADER bytes are not the encoding of the decoded fields
    as specified in ISCC-SEQ Format, item C.
2. Reject the ISCC-SEQ if ISCC-SEQ Format, item A does not permit the MainType, or if the Length
    field is greater than 7.
3. Reject the ISCC-SEQ if fewer bytes remain than the ISCC-BODY requires.
4. Output the ISCC-UNIT and move the offset to the end of its ISCC-BODY. If bytes remain, continue
    with step A.

A decoder shall not reject an ISCC-UNIT only because its SubType or Version is unknown to it. A
decoder shall not alter, reorder or drop ISCC-UNITs.

### Assertion

A `c2pa.soft-binding` assertion that contains ISCC soft bindings shall satisfy Table 1.

**Table 1 – `c2pa.soft-binding` fields for `io.iscc.v0`**
{: style="text-align:center; font-size:smaller" }

| **Field**         | **Requirement**                                                                                                                                                                                     |
| ----------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `alg`             | shall be `io.iscc.v0`                                                                                                                                                                               |
| `blocks[].scope`  | shall be an empty map; a validator or resolver shall ignore a block with a non-empty `scope`                                                                                                        |
| `blocks[].value`  | shall be a CBOR byte string (major type 2) whose content is the bytes of an ISCC-SEQ of 256-bit ISCC-UNITs, or a CBOR array of unsigned integers from 0 to 255 whose items are these bytes in order |
| `alg-params`      | not defined for `io.iscc.v0`; a validator or resolver shall ignore it                                                                                                                               |
| `bindingMetadata` | shall contain the member `io.iscc.generator`                                                                                                                                                        |

A claim generator should write `blocks[].value` as a byte string. A validator or resolver shall
accept both forms. Neither form shall contain a text encoding of the ISCC-SEQ, such as its canonical
form.

!!! note "NOTE 1"

    c2pa-rs up to at least version 0.91.7 writes the array form for a soft binding assertion given as
    JSON in a manifest definition
    ([c2pa-rs issue 2689](https://github.com/contentauth/c2pa-rs/issues/2689)).

The member `io.iscc.generator` shall be a map with two text string members:

1. `name`: the name of the software that generated the ISCC-UNITs, for example `iscc-sdk`;
2. `version`: the version of that software, for example `0.9.7`.

If `bindingMetadata` contains the member `informationalUrl`, its value should be
`https://ieps.iscc.codes/iep-0020/`.

A validator or resolver shall not reject an assertion because its `bindingMetadata` is absent or
because of its content.

A claim generator that computes an ISCC soft binding should list its `c2pa.soft-binding` assertion
in `created_assertions`. A validator or resolver shall not ignore or reject an ISCC soft binding
because it is listed in `gathered_assertions`.

A validator or resolver shall ignore, for matching, each ISCC-UNIT that it does not support or whose
ISCC-BODY is shorter than 256 bits.

A claim generator shall include the Data-Code and the Instance-Code of the source in each ISCC soft
binding. It should include a Content-Code if the source contains text, image, audio or video
content. It may include a Semantic-Code if supported by the claim generator. It may
include a Meta-Code. It should not include a featureless Image-Code.

A C2PA Manifest should contain at most one ISCC soft binding.

!!! note "NOTE 2"

    ISO 24138:2024 does not define an algorithm for the Semantic-Code. The Version 0 Semantic-Codes for
    text and image are those of [iscc-sct](https://github.com/iscc/iscc-sct) and
    [iscc-sci](https://github.com/iscc/iscc-sci). They are generated with neural network models.
    Semantic-Codes generated from the same content on different platforms or by different
    implementations can therefore differ in some bits.

## Soft Binding Input

A claim generator shall generate each ISCC-UNIT of an ISCC soft binding from the complete source.

!!! note "NOTE"

    A Meta-Code is thus generated from metadata embedded in the source, such as its title, not from a
    file name. iscc-sdk leaves it out if the source has no embedded title.

## Verification

To verify an ISCC soft binding against an asset, a validator shall generate from the asset an
ISCC-UNIT with the same MainType, SubType, Version and Length for each ISCC-UNIT of the ISCC soft
binding that it supports.

A validator or resolver shall compare two ISCC-SEQs by pairs of ISCC-UNITs, one from each, with the
same MainType, SubType, Version and Length: Instance-Codes for equality, all others by their
similarity in percent, *S* = ⌊100 × (*n* − *d*) / *n*⌋, where *d* is the number of bit positions in
which the two ISCC-BODYs differ and *n* is the length of an ISCC-BODY in bits. It shall not compare
a pair of Image-Codes if either is featureless.

!!! note "NOTE 1"

    *S* is 100 for equal ISCC-BODYs and about 50 for unrelated inputs.

!!! note "NOTE 2"

    Featureless Image-Codes occur for uniform images, brightness gradients along one axis and plain
    stripes. Featureless Image-Codes of unrelated images can be as close as Image-Codes of the same
    image.

## Matching

An ISCC soft binding and an ISCC-SEQ match on an exact match or on a candidate match. A candidate
match is a pair of their Semantic-Codes, Content-Codes or Data-Codes whose similarity is at or above
the threshold that the validator or resolver applies to that MainType and SubType. A validator or
resolver without thresholds of its own should apply a threshold of 80 (*d* ≤ 51).

A `c2pa.soft-binding` assertion with `alg` equal to `io.iscc.v0` matches if one of its ISCC soft
bindings matches. This is the matching to which Validating Soft Binding Matches of the C2PA
Technical Specification refers.

!!! note "NOTE 1"

    Suitable thresholds depend on the MainType and SubType, the content and the catalog size.

The score of a match is 100 for an exact match. Otherwise, it is the highest similarity of a pair of
Semantic-Codes, Content-Codes or Data-Codes, but at most 99. A resolver shall return the score as
`similarityScore` in the Soft Binding Resolution API. Matches should be listed in descending order
of score. An application should show for each match the similarity of every compared pair and
whether the Instance-Codes are equal.

Validating a Match of the C2PA Technical Specification applies to each matching C2PA Manifest.

!!! note "NOTE 2"

    An exact match shows that the query asset has the bytes from which the ISCC soft binding was
    generated. The hard binding of the C2PA Manifest can still fail for the query asset, because these
    bytes lack the C2PA Manifest Store that the claim generator embedded.

## Soft Binding Resolution API

In a query to the C2PA Soft Binding Resolution API with `alg` equal to `io.iscc.v0`, `value` shall
be the base64 encoding of an ISCC-SEQ with padding characters, as specified in RFC 4648, section 4.

## Security Considerations

The claim signature protects an ISCC soft binding through the hashed URI of its assertion. An
ISCC-SEQ has no integrity protection of its own.

Only the Instance-Code is a cryptographic hash. A match of any other ISCC-UNIT shows that two inputs
are similar, not that they are identical. Unrelated content can have similar ISCC-UNITs, and an
attacker can alter content until its ISCC-UNITs come close to those of other content. A secondary
check of each candidate, suited to the media type, guards against both.

An Instance-Code in a C2PA Manifest is public, and anyone can copy it into another C2PA Manifest. An
exact match therefore does not show that the other assertions of a candidate apply to the query
asset, or who created the content.

## Reference Implementation

[iscc-core](https://github.com/iscc/iscc-core) 1.5.0 encodes and decodes ISCC-SEQs (`encode_seq`,
`decode_seq`). Earlier versions generate 256-bit Image-Codes that differ from those of the test
vectors.

[iscc-sdk](https://github.com/iscc/iscc-sdk) 0.9.7 generates ISCC soft bindings as specified in this
document. The Python function `iscc_sdk.soft_binding()` returns the ISCC-UNITs and the ISCC-SEQ. The
command `iscc-sdk soft-binding FILE` prints the assertion, as in the EXAMPLE in Assertion. Its
option `--no-semantic` leaves out Semantic-Codes. The function `is_featureless_image_code()` tests
whether an Image-Code is featureless.

| (empty)                                                                | no ISCC-UNIT                                                |

    The 32-bit acceptance test exercises the ISCC-SEQ codec only. It is not a conforming ISCC soft

### Soft Binding Generation

The file
[`c2pa_vectors.json`](https://github.com/iscc/iscc-sdk/blob/main/iscc_sdk/c2pa_vectors.json) of
iscc-sdk gives, for each input, its SHA-256 hash, the expected ISCC-UNITs and the ISCC-SEQ in hex
and base64. An input is either a file of [iscc-samples](https://github.com/iscc/iscc-samples), given
by its path relative to the `files/` directory, or an embedded image. One embedded image is
featureless, so its ISCC soft binding has no Image-Code. Four embedded images have borders. For
these, `image_crop` gives the box (left, upper, right, lower) to which the image is cropped before
Image-Code generation.

A claim generator should generate the same Meta-Codes, Content-Codes, Data-Codes and Instance-Codes
from these inputs. The vectors contain no Semantic-Codes (see NOTE 2 in Assertion).

!!! note "NOTE"

    [IEP-0004](iep-0004.md) specifies Image-Code conformance for the pre-processed 32 × 32 pixel input
    only. The Image-Codes of the vectors use the border trim of iscc-sdk 0.9.7 (`image_trim_tolerant`).
